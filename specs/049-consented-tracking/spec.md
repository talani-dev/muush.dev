## User Scenarios & Testing *(mandatory)*

### User Story 1 - Nothing is tracked until the visitor says yes, per category (Priority: P1)

A visitor lands on any page in either language. The cookie banner appears. Until they accept a category, the site makes no request to Google or Meta. If they accept only Analytics, Google Analytics starts and Meta does not; if they accept only Advertising, the Meta Pixel starts and Google Analytics does not; "Accept all" starts both; "Decline all" starts neither.

**Why this priority**: This is the legal and ethical core of the feature: the privacy notice promises consent before measurement. Everything else depends on this gate being correct.

**Independent Test**: In a fresh browser profile, open `/es` and `/en` with the network panel filtered on `google`, `facebook`, `fbevents`: zero requests before a choice; then each of the four choices produces exactly the expected set of requests.

**Acceptance Scenarios**:

1. **Given** a first visit with no stored choice, **When** any page loads and the visitor scrolls and clicks around without answering the banner, **Then** no script, pixel or beacon request goes to any Google Analytics/Google Tag or Meta domain.
2. **Given** the preferences dialog, **When** the visitor turns on only "Analítica" and saves, **Then** Google Analytics loads and records the current page view, and no Meta request is made.
3. **Given** the preferences dialog, **When** the visitor turns on only "Publicidad" and saves, **Then** the Meta Pixel loads and records the current page view, and no Google Analytics request is made.
4. **Given** the banner, **When** the visitor chooses "Aceptar todo" / "Accept all", **Then** both load; **When** "Rechazar todo" / "Decline all", **Then** neither loads.
5. **Given** a returning visitor whose stored choice grants a category, **When** they open any page, **Then** only the granted tools load, without the banner appearing.

---

### User Story 2 - The visitor can change their mind, and the choice expires (Priority: P1)

A visitor who accepted a category later opens "Cambiar mis preferencias" (privacy page) and turns it off. The site stops sending data to that tool immediately and removes the tool's cookies from muush.dev; from the next page load the tool is not loaded at all. Twelve months after any choice, the banner asks again.

**Why this priority**: Revocation and expiry are what make consent meaningful; acceptance items 3 and 5.

**Independent Test**: Accept all, navigate, then revoke Advertising: no further Meta request on in-app navigation, `_fbp` is gone, and a reload loads no Meta script. Set a stored choice dated 12 months + 1 day ago: the banner reappears and nothing loads.

**Acceptance Scenarios**:

1. **Given** Analytics was granted and is running, **When** the visitor revokes it, **Then** no further Google Analytics request is sent during the visit, the `_ga` and `_ga_*` cookies are removed from muush.dev, and on the next page load Google Analytics is not loaded.
2. **Given** Advertising was granted and is running, **When** the visitor revokes it, **Then** no further Meta request is sent during the visit, the `_fbp` cookie is removed from muush.dev, and on the next page load the pixel is not loaded.
3. **Given** a stored choice made 12 months ago or more (accepted or rejected), **When** the visitor opens any page, **Then** the choice counts as absent: the banner shows and nothing loads until they answer again.
4. **Given** a stored choice made under feature 48 (Advertising only, no Analytics answer), **When** the visitor returns, **Then** the banner asks again (the new category was never answered).

### User Story 3 - The preferences dialog offers an Analytics category and names Google Analytics (Priority: P1)

The preferences dialog lists three categories, in this order: Necesarias (always on), **Analítica** (new, switch), Publicidad (switch). The Analytics row is visually identical to the Advertising row (same component, tokens, switch and spacing; no new visual value). The banner text and the dialog name Google Analytics. All copy exists in ES and EN.

**Why this priority**: Without a separate category the visitor cannot accept measurement without advertising; acceptance items 2 and 4.

**Independent Test**: Open the dialog at 390 px and 1440 px in both locales; the new row matches the Advertising row pixel-for-pixel apart from its text; the copy matches the approved drafts.

**Acceptance Scenarios**:

1. **Given** the dialog is open, **When** it renders, **Then** the categories appear as Necesarias → Analítica → Publicidad (EN: Necessary → Analytics → Advertising), each optional one with its own switch, both off when no choice exists.
2. **Given** either locale, **When** the banner or dialog renders, **Then** every string comes from the locale files and matches the approved copy of `copy-drafts.md` § B.

### User Story 4 - Roberto can read the visitor journey and the funnel in GA4 (Priority: P2)

With Analytics accepted, GA4 receives automatic page views (once per route change, not on in-page anchor jumps) and the custom events of the measurement plan: CTA clicks, contact clicks, form view/start/step/submit/error, lead, application submit, CV attach result, language change, cookie-preference change, and time per section on Home and Nosotros sent each time the visitor leaves a section. Key conversions also go to Meta (Schedule, Contact, Lead) when Advertising is accepted. No event carries personal data.

**Why this priority**: It is the business reason for the feature, but it is only allowed after Stories 1–3 hold.

**Independent Test**: With GA4 DebugView (or the network payloads) open, walk the journey "land on /es → read services → click Diagnóstico gratis in the hero → fill and send the assessment form" and see the expected event sequence with only fixed-id parameter values.

**Acceptance Scenarios**:

1. **Given** Analytics is granted, **When** the visitor moves between pages, **Then** exactly one page view is recorded per route change, and the in-page jump to the assessment anchor records none.
2. **Given** Analytics is granted, **When** the visitor triggers any event of the catalogue (FR-020), **Then** it is sent with its name and only the parameters listed for it, each a fixed id, boolean or number.
3. **Given** Analytics is granted on Home or Nosotros, **When** the visitor scrolls a section into view for ≥ 1 s and then leaves it (scroll away, navigate, hide the tab), **Then** one `section_view` with `page_key`, `section` and `section_seconds` (capped at 600) is sent; visits under 1 s send nothing.
4. **Given** Advertising is granted, **When** the visitor books a call, contacts by WhatsApp/email, or the assessment API confirms the request, **Then** Meta receives `Schedule`, `Contact` or `Lead` respectively; the talent application never produces a Meta event.
5. **Given** any granted category, **When** any event is sent, **Then** no name, email, phone, company, free text, CV data, URL typed by the visitor or IP appears in any event name or parameter.

### User Story 5 - Advanced matching for the assessment lead, covered by the notice (Priority: P2)

When a visitor who accepted Advertising sends the assessment form and the API confirms it, the Lead sent to Meta carries the email and (only if they chose WhatsApp) the phone with its country code, which the pixel hashes in the browser before sending. The privacy notice, in both languages, explains this with the text Roberto approved.

**Why this priority**: Improves ad attribution, but it is the one exception to "no personal data", so it only ships with its legal text (acceptance items 8–9).

**Independent Test**: With Advertising on, send the assessment form against a test endpoint: the Lead request to Meta carries hashed `em`/`ph` values only; with Advertising off, nothing goes to Meta; the application form never sends anything to Meta.

**Acceptance Scenarios**:

1. **Given** Advertising is granted, **When** the assessment API answers `ok: true`, **Then** Meta receives a Lead whose user data is limited to the hashed email and, if WhatsApp was chosen, the hashed phone (country code + number); no other form field is sent.
2. **Given** Advertising is not granted, **When** the form is sent, **Then** no form value reaches Meta or Google.
3. **Given** the approved notice text has not been approved at the gate, **When** the feature is built, **Then** advanced matching is not part of the release (FR-031).

### User Story 7 - The assessment form asks for the visitor's website or social media (Priority: P2)

A visitor filling in the assessment ("diagnóstico") form can optionally tell muush where their business lives online: a site, a domain or a social handle, typed however they like. The field sits where the design puts it, is sent with the request when filled in, and is left out entirely when empty. It never reaches Google or Meta. The talent application form does not have it.

**Why this priority**: It helps muush prepare the assessment (the "Lo que recibes" list promises a review of the visitor's site), but the form already works without it, and it depends on the API release that accepts the key (R43).

**Independent Test**: At 1440 px and 390 px, in both locales, find the field in its position; send the form against a stubbed API with a value, with spaces only and with nothing; inspect the request body and the GA4/Meta payloads.

**Acceptance Scenarios**:

2. **Given** the form at mobile width, **When** the visitor reaches step 2, **Then** the field appears between "¿Cómo te identificas?" and "¿Qué necesitas?"; step 1 is unchanged.
3. **Given** the visitor typed `  casaolivo.mx  `, **When** the form is sent, **Then** the assessment request carries `website: "casaolivo.mx"` (trimmed, otherwise as typed: `@handle`, a domain without scheme and a full URL are all accepted, no URL check).
4. **Given** the field is empty or holds only spaces, **When** the form is sent, **Then** the request has no `website` key at all (not `""`, not `null`).
5. **Given** the talent application form, **When** it is sent, **Then** its request never carries a `website` key, and the hidden anti-spam field keeps its own name, which is never `website` and never sent.
6. **Given** any consent state, **When** the form is viewed, started, sent or fails, **Then** the field's value appears in no GA4 or Meta event and is not part of Meta advanced matching.

### Edge Cases

- **Storage blocked** (private mode, quota): the choice holds for the visit (feature 48 behaviour); tools load only for what was granted in that visit; nothing is remembered.
- **Tampered or future-dated stored choice** (`decidedAt` unparseable or later than now): counts as no choice; the banner asks again.
- **Choice made in one tab, other tab open**: the other tab follows its own in-memory state until reloaded; it never loads a tool the stored choice does not grant at its own load time.
- **Script blocked by an ad blocker / network failure**: the site keeps working; events are silently dropped; no error is shown and no retry loop runs.
- **Revoke then re-grant in the same visit**: the tool resumes sending (new page view); a fresh `_ga`/`_fbp` may be issued.
- **Visitor accepts after scrolling**: page view for the current page is recorded once at grant time; sections already left before the grant are not reported retroactively.
- **Mobile tab killed**: the last open `section_view` may be lost (known limit, tracking plan § 5).
- **404 pages**: consent and page views behave as on any page (`cta_location` = `not_found`); no section timing.
- **Email-preference lead**: advanced matching sends the email only; no phone field exists.
- **Prerendered HTML**: contains no tracking script tag and no `<noscript>` pixel, ever.
- **Website, whitespace only** (spaces, tabs, line feed pasted): counts as empty; the `website` key is absent from the request.
- **Website, length limit**: the limit is 300 Unicode code points of the **trimmed** value (an emoji counts as 1). Exactly 300 code points (for example 299 letters + 1 emoji, which is 301 UTF-16 units) is sent; 301 code points is never sent. The input also carries `maxlength="300"`, which browsers count in UTF-16 units, so through the input the visitor can never exceed the limit (a run of emoji stops at 150); the code-point rule in the request builder is the backstop (FR-063).
- **Website over the limit anyway** (a browser that ignores `maxlength`, a programmatic value): no request is sent and the visitor sees the form's existing generic send error; no new message (FR-064).
- **Server rejects `website`** (`400 validation_failed` naming `website`, e.g. the API release is not live): the visitor sees the existing generic send error, values kept, retry possible. This is the R43 failure mode; the deploy precondition prevents it.
- **Website looks like a URL to the browser**: the input is a plain text input, so `@handle` or `casa olivo` never triggers a native URL error.

## Requirements *(mandatory)*

### Functional Requirements

**Consent model**

- **FR-001**: The consent record MUST cover two optional categories, `analytics` and `advertising`, plus the always-on `necessary`. A stored record that does not answer both optional categories MUST count as no choice.
- **FR-002**: A stored choice MUST expire 12 calendar months after its `decidedAt`, whether it granted or refused; an expired, unparseable or future-dated record MUST count as no choice (banner shows, nothing loads).
- **FR-003**: The preferences dialog MUST list Necesarias → Analítica → Publicidad, with the Analytics row rendered by the existing category-row component with no new visual value (no new token, utility, spacing or variant).
- **FR-004**: Banner, dialog and privacy-notice copy MUST come from `i18n/locales/{es,en}.json`, equal to the text Roberto approves in `copy-drafts.md`, copied literally; i18n parity holds.

**Loading and revoking**

- **FR-010**: No script, pixel, beacon or other request to Google Analytics/Google Tag or Meta domains MUST occur before the matching category is granted; the prerendered HTML MUST contain no tracking script tag and no `<noscript>` pixel.
- **FR-011**: Granting `analytics` MUST load Google Analytics 4 (measurement ID from public build configuration) and record the current page view; granting `advertising` MUST load the Meta Pixel (ID from public build configuration) and record the current PageView. Each tool is independent of the other's category.
- **FR-012**: Revoking a category MUST stop all further sends to that tool for the rest of the visit, remove that tool's first-party cookies from muush.dev (`_ga`, `_ga_<container>` for Analytics; `_fbp` for Advertising), and the tool MUST NOT load on the next page load.
- **FR-013**: Both IDs MUST live in public runtime configuration, never written in a component or composable (Constitution Article XI).
- **FR-014**: Google Analytics MUST be configured with a `_ga` cookie lifetime that never exceeds 14 months, Google Signals and ad-personalisation signals off, no User-ID, and no user-provided data.
- **FR-015**: The Meta Pixel MUST run with automatic configuration (automatic events/metadata) off; no `<noscript>` fallback; automatic advanced matching stays off on Meta's side (Roberto, Events Manager).

**Measurement plan**

- **FR-020**: With Analytics granted, the site MUST send exactly the custom events of tracking plan § 4 (`assessment_cta_click`, `book_call_click`, `contact_click`, `form_view`, `form_start`, `form_step`, `form_submit`, `form_error`, `generate_lead`, `form_response` (FR-027), `cv_attached`, `application_submit`, `language_change`, `section_view`, `cookie_preferences`), each with only its listed parameters.
- **FR-021**: Every parameter value MUST be a fixed id from a closed list, a boolean or a number; free text is impossible by construction. `cta_location` values are the closed set of places the CTA exists on the built site (nav, hero, mobile_menu, footer, faq, not_found, form_success, and any other place found in the audit of the plan).
- **FR-022**: Page views MUST count once per route change; a hash-only change (in-page anchor jump) MUST NOT count as a page view.
- **FR-023**: `section_view` MUST follow tracking plan § 5: in view = ≥ 50 % of the section (or of the viewport for taller sections) visible while the tab is visible; one event per visit on leave; flush on page hide with a transport that survives unload; < 1 s not sent; capped at 600 s; Home sections `hero`, `who_we_are`, `services`, `how_we_work`, `assessment`; Nosotros sections `hero`, `how_it_comes_together`, `where_we_are`, `work_with_us`.
- **FR-024**: `cookie_preferences` MUST be sent only when a choice is saved while Analytics is granted after the save, with `analytics` and `ads` booleans.
- **FR-025**: With Advertising granted, Meta MUST receive `Schedule` on `book_call_click`, `Contact` on `contact_click` and `Lead` on `generate_lead`, plus PageView per route change (FR-022 rule). The talent application, CV and every other event MUST NOT reach Meta.
- **FR-027** *(amendment, Roberto 2026-11-07)*: With Analytics granted, each submission attempt of either form whose API call finished MUST send one GA4-only `form_response` with `form` (`assessment` | `application`), `result` (`ok` | `error`) and, only for `error`, `error_type` (`network`, `server`, `challenge_failed`, or `validation` for a server-side 400, whatever fields it names). It is reported once per attempt, after the single token retry; for the application with a CV, a failed upload request or a failed CV PUT (`server`) is the attempt's error and `/careers` is not called. An attempt that never reached the API (client-side validation, no Turnstile token) sends none. `generate_lead`, `application_submit` and `form_error` are unchanged. `form_response` never reaches Meta and carries no personal data (FR-026).
- **FR-026**: No event name or parameter sent to Google or Meta MUST ever contain a name, email, phone, company, the "¿Qué necesitas?" text, the website field (FR-060), CV data, a URL typed by the visitor or the IP, with the single exception of FR-030.

**Meta advanced matching**

- **FR-030**: With Advertising granted, when the assessment API confirms the request, the Lead MUST carry as user data only the email (trimmed, lowercased) and, if the contact preference is WhatsApp, the phone as country dial code + digits; the pixel hashes both (SHA-256) before sending. No other field, and nothing from the application form.
- **FR-031**: Advanced matching MUST ship only in the same release as the privacy-notice text Roberto approves for it (`copy-drafts.md` § A); if that text is not approved at the gate, FR-030 is removed from this feature's scope.

**Privacy notice**

- **FR-035**: The privacy notice (ES and EN) MUST name Google Analytics in "Con quién los compartimos", cover Meta advanced matching, and correct every line this feature makes inaccurate, exactly as approved in `copy-drafts.md` § A; no other part of the notice changes.

**robots.txt and llms.txt**

- **FR-040**: robots.txt MUST remain generated by `@nuxtjs/robots` 6.x and MUST add two explicit groups that allow everything (same rule as `*`): AI search/answer agents `OAI-SearchBot`, `ChatGPT-User`, `Claude-SearchBot`, `Claude-User`, `PerplexityBot`, `Perplexity-User`; AI training agents `GPTBot`, `ClaudeBot`, `Google-Extended`, `Applebot-Extended`, `CCBot`. Tokens verified on 2026-11-07 against each provider's page (research.md R5).
- **FR-041**: robots.txt MUST keep `User-agent: *` allowing everything, MUST contain no `Disallow: /`, and MUST print `Sitemap: https://muush.dev/sitemap.xml` exactly once.
- **FR-042**: No robots file may exist under `public/` (feature 35 trap).
- **FR-045**: `/llms.txt` MUST exist at the site root, follow the llmstxt.org format (H1, blockquote summary, sections of Markdown link lists), contain the text Roberto approves (`copy-drafts.md` § C), and link exactly the 10 sitemap URLs as absolute `https://muush.dev/...` URLs.
- **FR-046**: llms.txt MUST contain no personal contact data and nothing not already published on the site.

**Assessment form: website field (scope item 8)**

- **FR-060**: The assessment form MUST show an optional text field labelled "Tu sitio web o redes (opcional)" (ES) / "Your website or social media (optional)" (EN) with placeholder "https://" in both locales, from `i18n/locales/{es,en}.json` exactly as in `copy-drafts.md` § D; i18n parity holds.
- **FR-061**: Position (from the `.pen`, leader extract 2026-11-07): at desktop width a full-width row below the "Empresa o proyecto" + "¿Cómo te identificas?" row and above "¿Qué necesitas?"; in the mobile two-step form, step 2, between "¿Cómo te identificas?" and "¿Qué necesitas?". It MUST reuse the form's existing text-field component and tokens: no new visual value.
- **FR-062**: The field MUST accept free text as typed (no URL parsing, no format error, plain text input) and MUST never be required; it never shows a field error of its own.
- **FR-063**: The assessment request MUST carry the key `website` with the trimmed value when the trimmed value is non-empty, and MUST omit the key when it is empty; the value is never `null` and never `""`. The trimmed value MUST be at most 300 Unicode code points; the input MUST carry `maxlength="300"`.
- **FR-064**: A trimmed value over 300 code points MUST NOT be sent; the form shows its existing generic send error (no new copy). A server `validation_failed` naming `website` MUST also end in the existing generic send error, with the visitor's values kept.
- **FR-065**: The talent application request MUST never carry `website`. The field's input MUST NOT use the anti-spam field's name `muush_website`, and the anti-spam field MUST stay out of every request.
- **FR-066**: The website value MUST NOT appear in any GA4 or Meta event, parameter, page view or advanced-matching user data (FR-026, FR-030).
- **FR-067**: Release precondition (not an implementation task): the API release that accepts `website` is live in production, confirmed by Roberto, before this feature is deployed (R43).

**Unchanged**

- **FR-050**: `sitemap.xml` MUST keep listing exactly the 10 URLs; the build MUST publish no `.map` file and no `sourceMappingURL`.
- **FR-051**: `pnpm check`, `pnpm typecheck`, `pnpm test`, `pnpm generate` and `pnpm storybook:build` MUST pass.

### Key Entities

- **Consent record**: version, `decidedAt`, answers for `analytics` and `advertising`; valid for 12 months.
- **Tracking event**: a name from the closed catalogue, parameters from closed value lists, destinations (GA4 always when granted; Meta only for the four mapped events).
- **Section visit**: page key, section id, start time, accumulated visible seconds; emitted once on leave.
- **Advanced-matching user data**: email and optional phone, present only on the Meta Lead, only with Advertising.
- **AI crawler group**: a set of user-agent tokens with an allow-everything rule.
- **Assessment request `website`**: optional free text, trimmed, 1–300 code points when present, absent when empty; assessment form only.

## Success Criteria *(mandatory)*
